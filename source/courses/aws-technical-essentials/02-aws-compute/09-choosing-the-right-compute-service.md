# Choosing the Right Compute Service

บทเรียนนี้นำเสนอในรูปแบบวิดีโอ "เกมโชว์" ที่ทบทวนบริการ compute ของ AWS ที่เรียนมาแล้ว (Amazon EC2, container services, AWS Lambda) ผ่านสถานการณ์ตัวอย่าง 3 สถานการณ์ โดยให้ผู้ชมทายว่าควรเลือกใช้ compute service ใด

## สถานการณ์ที่ 1: อัปเดตฐานข้อมูลสินค้าจากไฟล์ inventory
มีนักพัฒนาต้องสร้างฟีเจอร์ใหม่สำหรับเว็บแอปพลิเคชันร้านค้าออนไลน์ที่โฮสต์บน EC2 ปัจจุบันสินค้าถูกเพิ่มเข้าฐานข้อมูลด้วยมือ (มีคนเพิ่มแถวใหม่ในฐานข้อมูลทีละรายการ) โดยข้อมูล inventory ใหม่จะถูกอัปเดตเพียงไตรมาสละครั้งเท่านั้น

**คำตอบ: AWS Lambda**

เหตุผล:
- Amazon EC2 คิดค่าบริการตามวินาทีหรือชั่วโมง หากปล่อยให้ instance รันตลอดเวลาเพื่อรองรับกระบวนการที่เกิดขึ้นเพียงไตรมาสละครั้ง จะเป็นการเสียโอกาสด้านต้นทุน
- AWS Lambda คิดค่าบริการเฉพาะตอนที่โค้ดกำลังรันจริงเท่านั้น และโค้ดจะรันก็ต่อเมื่อมี trigger หรือถูกเรียกใช้โดยตรง
- แนวทางที่แนะนำ: ให้ผู้ใช้อัปโหลดไฟล์ inventory ไปยัง Amazon S3 แล้วตั้งค่า **PutEvent** จาก Amazon S3 เป็น trigger ของ Lambda function เมื่อมีการอัปโหลดไฟล์ Amazon S3 จะ trigger ให้ Lambda function ทำงาน โดยโค้ดใน function จะอ่าน (parse) ไฟล์ inventory และเพิ่มแต่ละรายการเข้าไปในฐานข้อมูล

## สถานการณ์ที่ 2: ย้ายแอปพลิเคชันจาก on-premises มายัง AWS
มีแอปพลิเคชันที่รันอยู่บน Linux server ใน data center แบบ on-premises ต้องการย้าย (migrate) มายัง AWS โดยต้องการลดปริมาณการ refactor ให้น้อยที่สุด และต้องการให้ workload มีความยืดหยุ่น (elastic) รองรับ demand ที่เปลี่ยนแปลงได้

**คำตอบ: Amazon EC2**

เหตุผล:
- เนื่องจากต้องการลด refactoring ให้น้อยที่สุด การใช้ Amazon EC2 เหมาะสมที่สุด เพราะสามารถ launch EC2 instance จาก Linux-based AMI และโฮสต์แอปพลิเคชันบน EC2 instance ได้เหมือนกับที่โฮสต์บน Linux server on-premises
- Amazon EC2 ยังสามารถ scale in/out ตาม demand ได้ด้วย
- เหตุผลที่ตัดตัวเลือกอื่นออก: AWS Lambda ไม่สามารถอัปโหลดโค้ดเดิมที่รันบน EC2 เข้าไปใช้ได้ทันที ต้องมีการ refactor พอสมควรจึงจะใช้ประโยชน์จากบริการนี้ได้ ในทำนองเดียวกัน container service อย่าง ECS/EKS ก็ต้องมีการปรับโค้ดในระดับหนึ่งเพื่อย้ายไปใช้ container เช่นกัน

## สถานการณ์ที่ 3: สร้างแอปพลิเคชันใหม่แบบ microservices
วางแผนเขียนแอปพลิเคชันใหม่ทั้งหมดด้วยสถาปัตยกรรมแบบ microservices หรือ service-oriented design ต้องการให้ scale ขึ้น/ลงได้อย่างรวดเร็ว และต้องการลดความเสี่ยงในการ deploy การเปลี่ยนแปลงไปยัง production

**คำตอบ: Container service (Amazon ECS หรือ Amazon EKS)**

เหตุผล:
- Container ช่วยรองรับการออกแบบแบบ microservice หรือ service-oriented ได้ง่ายกว่า
- Container เริ่มทำงาน (boot up) ได้เร็ว ทำให้ scale ได้เร็วกว่า EC2 instance
- Container ช่วยเรื่อง code portability — หากเขียนโค้ดบนเครื่องส่วนตัวแล้วรันใน container, ทดสอบใน QA ด้วย container เดียวกัน ก็สามารถคาดหวังได้ว่า container เดียวกันนี้จะทำงานเหมือนเดิมเมื่อ deploy ไปยัง production ช่วยลดความเสี่ยงที่การ deploy จะเกิดข้อผิดพลาดจากความแตกต่างของ environment

## สรุป
ควรทำความเข้าใจ use case ต่างๆ ของบริการ compute อื่นๆ ของ AWS เพิ่มเติม เพื่อประกอบการตัดสินใจออกแบบสถาปัตยกรรมอย่างเหมาะสม เพราะมีตัวเลือกให้พิจารณามากมาย ควรจดจำไว้ว่าแต่ละบริการถูกออกแบบมาให้เหมาะกับ use case ที่แตกต่างกัน — ไม่ควรใช้ compute service เดียวกันสำหรับทุก use case แต่ควรเลือกให้เหมาะกับงานนั้นๆ และพิจารณาทบทวนตัวเลือกสำหรับ workload ที่มีอยู่เดิมอยู่เสมอ เนื่องจาก AWS พัฒนาและปรับปรุงบริการอย่างต่อเนื่อง

## Key terms
- Amazon S3 PutEvent trigger: event ที่เกิดขึ้นเมื่อมีการอัปโหลดไฟล์เข้า S3 bucket ซึ่งสามารถใช้เป็น trigger ให้ Lambda function ทำงานได้
- Code portability: ความสามารถของ container ที่ทำให้โค้ดทำงานเหมือนกันในทุก environment (dev, QA, production)
- Refactoring: การปรับแก้โครงสร้างโค้ดเพื่อให้เหมาะกับ platform หรือบริการใหม่
