# Disaster Planning

บทเรียนนี้เจาะลึกเรื่องการวางแผนรับมือภัยพิบัติ (disaster planning) โดยจะเรียนรู้กลยุทธ์ต่าง ๆ ในการปกป้องแอปพลิเคชันเมื่อเกิดภัยพิบัติ มีวิดีโอผู้สอนความยาว 12:11 นาที ประกอบเนื้อหา

การทดสอบ (testing) ทรัพยากร (resources) และการวางแผน (planning) เป็นองค์ประกอบสำคัญของแผน disaster recovery (DR) ที่ประสบความสำเร็จ

## Availability concepts

ระบบ production มักมีเป้าหมายเรื่อง uptime ทั้งแบบที่กำหนดไว้ชัดเจนหรือโดยนัย ระบบจะถือว่ามี high availability เมื่อ downtime ถูกลดให้น้อยที่สุดในกรณีเกิดความล้มเหลว เนื้อหาส่วนนี้อธิบายผ่าน 4 หมวดหมู่ที่ต้องคลิกขยาย (accordion) ดังนี้:

### High Availability
High availability ช่วยลด downtime และค่าใช้จ่าย ปกป้องระบบจากความล้มเหลว ทำให้ธุรกิจดำเนินต่อไปได้โดยมี downtime น้อยมากและกู้คืนได้เร็วในราคาต้นทุนต่ำ

### Fault tolerance
Fault tolerance มักถูกสับสนกับ high availability แต่จริง ๆ แล้วหมายถึงความซ้ำซ้อน (redundancy) ที่สร้างไว้ในตัวส่วนประกอบของแอปพลิเคชันเพื่อป้องกันไม่ให้บริการหยุดชะงัก อย่างไรก็ตาม วิธีนี้มีต้นทุนสูงกว่า

### Backup
(เนื้อหาในหมวดนี้เน้นเรื่องการสำรองข้อมูล ซึ่งอธิบายรายละเอียดต่อในบทเรียน AWS Backup ถัดไปในโมดูลนี้)

### Disaster recovery
Disaster recovery มักถูกมองข้ามในฐานะองค์ประกอบของ availability หากภัยพิบัติทางธรรมชาติ (natural disaster) ทำให้ส่วนประกอบของระบบในพื้นที่หนึ่งได้รับผลกระทบ

## Failover and Regions

AWS มีให้บริการในหลาย Region ทั่วโลก คุณสามารถเลือกตำแหน่งที่เหมาะสมที่สุดสำหรับไซต์ DR ของคุณ นอกเหนือจากไซต์ที่ระบบหลักถูก deploy อยู่แบบเต็มรูปแบบ โอกาสที่ Region หนึ่งจะไม่พร้อมใช้งานนั้นต่ำมาก แต่ก็เป็นไปได้หากเกิดเหตุการณ์ขนาดใหญ่ระดับภูมิภาค เช่น ภัยพิบัติทางธรรมชาติ

AWS มีนโยบายแยก Region (Region isolation policy) อย่างเข้มงวด เพื่อให้เหตุการณ์ขนาดใหญ่ใน Region หนึ่งไม่ส่งผลกระทบต่อ Region อื่น ๆ AWS สนับสนุนให้ลูกค้าใช้แนวทาง multi-Region ในลักษณะเดียวกันสำหรับกลยุทธ์ของตนเอง โดยแต่ละ Region ควรสามารถถูกนำออกจากระบบ (taken offline) ได้โดยไม่กระทบ Region อื่น

## Recovery Point Objective (RPO) และ Recovery Time Objective (RTO)

**RPO** คือปริมาณข้อมูลที่ยอมรับได้ว่าจะสูญหาย วัดเป็นหน่วยเวลา ตัวอย่างเช่น หากเกิดภัยพิบัติเวลา 13:00 น. และ RPO คือ 12 ชั่วโมง ระบบควรกู้คืนข้อมูลทั้งหมดที่มีอยู่ก่อนเวลา 01:00 น. ของวันเดียวกัน หมายความว่าข้อมูลจะสูญหายมากที่สุดไม่เกินช่วง 12 ชั่วโมง (ระหว่าง 13:00 น. ถึง 01:00 น.)

**RTO** คือระยะเวลาหลังจากเกิดเหตุขัดข้องจนกว่ากระบวนการทางธุรกิจจะกลับมาอยู่ในระดับบริการที่กำหนดไว้ใน operational level agreement (OLA) ตัวอย่างเช่น หากเกิดภัยพิบัติเวลา 13:00 น. และ RTO คือ 1 ชั่วโมง กระบวนการ DR ควรทำให้กระบวนการทางธุรกิจกลับมาอยู่ในระดับบริการที่ยอมรับได้ภายในเวลา 14:00 น.

## Essential AWS services และ features สำหรับ Disaster Recovery

เมื่อวางแผน DR สิ่งสำคัญคือต้องพิจารณาบริการและฟีเจอร์ที่รองรับการย้ายข้อมูล (data migration) และการจัดเก็บข้อมูลแบบทนทาน (durable storage) สำหรับบางสถานการณ์ที่เกี่ยวข้องกับการ deploy ระบบแบบลดขนาดหรือเต็มรูปแบบบน AWS จะต้องมีทรัพยากร compute ด้วยเช่นกัน

ในระหว่างเกิดภัยพิบัติ คุณต้อง provision ทรัพยากรใหม่หรือ failover ไปยังทรัพยากรที่ preconfigured ไว้ล่วงหน้า ทรัพยากรเหล่านี้รวมถึง code และ content แต่ก็อาจรวมถึงส่วนอื่น ๆ เช่น DNS entries, network firewall rules และ virtual machines/instances

เมื่อวางแผนกลยุทธ์การ backup ควรวางแผนทำสำเนา storage ของคุณโดยใช้โซลูชันที่ตอบโจทย์ความต้องการในการกู้คืน AWS มีตัวเลือกสำหรับการทำสำเนาข้อมูลใน storage ผ่านหัวข้อ (tabs) ต่าง ๆ ได้แก่ Duplicate your storage, Configuring AMI for recovery, Failover network design, Database backup and replicas, และ Templates and scripts (เนื้อหารายละเอียดในแต่ละแท็บไม่สามารถเปิดดูได้ครบถ้วนระหว่างการดึงข้อมูล เนื่องจากหน้าเว็บไม่เสถียร)

Disaster recovery เป็นพื้นที่กว้างขวางที่ต้องสำรวจ และแอปพลิเคชันแต่ละแบบก็มีชุดคุณลักษณะเฉพาะที่ต้องปกป้องแตกต่างกันไป เมื่อได้ภาพรวมของบริการที่มีสำหรับ disaster recovery แล้ว คุณสามารถวางแผน disaster recovery ตามความต้องการของแอปพลิเคชันของคุณได้

## Key terms
- High availability (HA): การออกแบบให้ downtime น้อยที่สุดเมื่อเกิดความล้มเหลว
- Fault tolerance: ความซ้ำซ้อนในตัวระบบเพื่อป้องกันบริการหยุดชะงัก
- RPO (Recovery Point Objective): ปริมาณข้อมูลสูงสุดที่ยอมรับได้ว่าจะสูญหาย วัดเป็นเวลา
- RTO (Recovery Time Objective): เวลาที่ยอมรับได้ในการกู้คืนระบบกลับสู่ระดับบริการปกติ
- Region isolation policy: นโยบายของ AWS ที่แยกผลกระทบของเหตุการณ์ในแต่ละ Region ออกจากกัน
